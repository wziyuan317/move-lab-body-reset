## 六、图片与帧状态接入

当前网页只认识：

```js
frames: {
  start: "...",
  end: "...",
}
```

融合后必须支持统一的可用帧数组：

```js
frames: [
  { id: "start", label: "起始状态", sourceKey: "起始", src: "..." },
  { id: "process", label: "运动过程", sourceKey: "过程", src: "..." },
  { id: "end", label: "到位状态", sourceKey: "到位", src: "..." },
]
```

- 静态动作只有 `start` 和 `end`。
- 动态动作必须显示 `start`、`process`、`end`，不能丢弃“过程”帧。
- 切换动作时自动回到该动作第一帧。
- 图片按钮根据动作实际帧数生成，不写死为两个按钮。
- 图片 `alt` 必须包含动作名称和帧名称。
- 图片使用 `loading="lazy"`；列表使用独立缩略图，不直接加载 1 MB 以上的原图。
- 原始 PNG 保留在内容包内。允许在构建阶段生成 WebP/AVIF 详情图和小缩略图，但派生图不得反向覆盖原图。

## 七、推荐的数据接入方式

不要把 83 个动作手工复制进 `src/movements.js`。

建立一个确定性的构建脚本，例如：

`scripts/content-library/build-web-library.mjs`

它应当：

1. 读取 `动作/动作总索引.json`。
2. 逐项读取动作 `内容.json` 和 `图像语义.json`。
3. 生成网页专用数据，例如 `src/generated/stretchingMovements.json`。
4. 生成或复制网页图片到 `public/assets/stretching-anatomy/<动作ID>/`。
5. 保留动作 ID、肌肉 ID、身体区域 ID、页面 ID 和来源路径。
6. 对输出排序保持稳定，重复执行得到相同结果。
7. 失败时明确报出动作 ID 和文件路径，不能静默跳过。

`src/movements.js` 可以继续保存原有 15 个办公室动作；通过一个聚合模块把“办公室动作”和“书籍动作”合并给页面使用。

## 十、姿势图片质量约束

- `验证/姿势差异审计.json` 记录 83 个动作的 93 组相邻帧判断和图片哈希。
- 起始、过程、到位必须有可见的关键关节位置差异，不能只移动箭头、文字或肌肉高亮。
- 如果修改任何动作图片，必须重新人工看图，并更新对应审计哈希。
- 中级跪姿腕屈肌拉伸必须显示：双掌贴地、指尖朝膝、臀部从膝上方向脚跟后移。

- 图片中的动作方向不得与文字步骤相反。
